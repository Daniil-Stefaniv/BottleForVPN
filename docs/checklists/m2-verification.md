# Чеклист ручной приёмки M2

Дата: 2026-10-01 · Этап: M2 (host-бутылки + служба маршрутов + живучесть,
спека §14)

Чеклист закрывает критерий готовности M2: *«Destructive-набор проходит;
host-бутылка с реальным клиентом работает параллельно с env»*. Проводится
вручную на машине с Windows 10/11 и WSL2 (режим сети NAT — по умолчанию).

Подготовка (общая для всех пунктов):

- собраны `bottled.exe`, `bottle.exe` и `bottle-svc.exe`
  (`cargo build --release -p daemon -p cli -p svc`);
- **пересобран rootfs-аплаенс** (`bash appliance/build-rootfs.sh`, нужен
  docker) — `artifacts\bottleforapps-rootfs.tar.gz`. Протокол
  демон↔агент обновился до версии 2 (instance-поколения): образ,
  собранный в M1, НЕсовместим с демоном M2 — приёмку по старому rootfs
  проводить нельзя (демон сообщит о несовпадении версий). Переположите
  образ в `<DataDir>\appliance\`;
- установлена служба маршрутов: **PowerShell от имени администратора**,

  ```powershell
  C:\Tools\BottleForApps\bottle-svc.exe --install
  sc.exe query BottleForAppsRouteHelper   # RUNNING — служба уже поднялась
  ```

  (автозапуск, LocalSystem; устанавливается один раз);
- демон запущен: `bottled --data-dir <DataDir>` (каталог данных лучше
  держать отдельным, чтобы приёмку можно было повторить с чистого
  состояния);
- env-бутылка — **реальный конфиг WireGuard/OpenVPN** (рабочий, с доступом
  до какого-нибудь RDP/HTTP-узла в VPN-сети), профиль `kind = "env"` —
  формат как в [чеклисте M1](m1-verification.md);
- host-бутылка — **реальный фирменный VPN-клиент** (Cisco AnyConnect,
  FortiClient, GlobalProtect и т.п.), установленный и настроенный на
  рабочее подключение; профиль `kind = "host"` (формат — README, раздел
  «Host-бутылки»):

  ```toml
  id = "corp-vpn"
  name = "Корп VPN"
  kind = "host"

  [vpn]
  client = 'C:\Program Files\Vendor\vpn.exe'
  args = "connect office"
  endpoints = ["vpn.example.com"]

  [expose]
  socks5 = 0
  forwards = [{ listen = 0, target = "10.50.10.15:3389" }]
  ```

  `interface` указывайте, если у вендора несколько виртуальных адаптеров;
  иначе демон ждёт «единственный новый Up-адаптер» после запуска клиента
  (до 120 с);
- журнал маршрутов службы: `%PROGRAMDATA%\BottleForApps\routes.jsonl`
  (append-only, строки `{op, dest, session, ts}`) — пригодится в пунктах
  2–4.

Обозначение результата: каждый пункт помечается `[ ]` при провале либо
`[x]` при успехе; при провале заполняется «Что смотрели».

---

## 1. Host-бутылка с реальным клиентом + env-бутылка одновременно

**Шаги.**
1. `bottle start office-a` (env, WireGuard/OpenVPN) — дождаться `up`.
2. `bottle start corp-vpn` (host, фирменный клиент) — демон добавит
   точечные маршруты endpoint'ов, запустит клиент и дождётся его
   VPN-адаптера (поллинг 2 с, лимит 120 с).
3. `bottle status` — обе бутылки.
4. RDP через обе: `mstsc /v:127.0.0.1:<порт env>` и
   `mstsc /v:127.0.0.1:<порт host>`.
5. `curl.exe https://api.ipify.org` напрямую — интернет на компьютере.

**Ожидаемый результат.** Обе бутылки `up`, у каждой свои строки
`socks5`/`rdp` с разными портами; обе RDP-сессии работают одновременно;
прямой curl отвечает обычным внешним IP физической сети — default route
хоста не перехвачен в пользу одного из VPN (endpoint host-бутылки идёт
по точечному маршруту, env-бутылка целиком в WSL).

**Где смотреть при провале.** `bottle show corp-vpn` — причина в
`failed (...)`: «интерфейс не появился» (клиент не подключился? неверный
`interface` в профиле?), «несколько новых интерфейсов» (укажите
`interface` явно); служба: `sc.exe query BottleForAppsRouteHelper`
(RUNNING?); журнал демона — вывод `bottled` в консоли (резолв endpoint'ов,
шлюз физики, поллинг адаптеров); журнал маршрутов
`%PROGRAMDATA%\BottleForApps\routes.jsonl`.

## 2. Endpoint'ы обеих бутылок идут через физику

**Шаги.**
1. Выписать IP endpoint'а host-бутылки (резолв `vpn.example.com`,
   например `nslookup vpn.example.com`).
2. PowerShell: `Get-NetRoute | findstr <endpoint-ip>` (проверить до и
   после старта host-бутылки).
3. На WG/OpenVPN-сервере env-бутылки посмотреть, с какого адреса приходит
   клиент: `wg show` (поле `endpoint` пира) либо
   `tcpdump -ni any udp port <порт сервера>`.

**Ожидаемый результат.** После старта host-бутылки у её endpoint'а
появляется маршрут `/32` (для IPv6 — `/128`) c `NextHop` = шлюз физической
сети и `InterfaceAlias` физического адаптера (Wi-Fi/Ethernet), а не
VPN-адаптер вендора; маршрут лежит в `ActiveStore` (исчезнет после
перезагрузки — так задумано). На сервере env-бутылки виден публичный IP
физической сети хоста (как в M1): WSL-NAT выводит трафик VM через
физику, минуя чужие туннели.

**Где смотреть при провале.** `route print <endpoint-ip>`;
`%PROGRAMDATA%\BottleForApps\routes.jsonl` (был ли `add` для этого dest);
`Get-NetRoute -DestinationPrefix 0.0.0.0/0 | sort InterfaceMetric` —
какой адаптер держит default route (если VPN-адаптер — точечный маршрут
обязан существовать, иначе трафик endpoint'а уйдёт в чужой туннель);
журнал демона — строка про выбранный шлюз физики.

## 3. kill -9 демона убирает маршруты (сессия умирает с pipe)

**Шаги.**
1. Host-бутылка поднята; `Get-NetRoute | findstr <endpoint-ip>`
   показывает её маршруты.
2. `taskkill /f /im bottled.exe`.
3. Каждые ~2 с повторять `Get-NetRoute | findstr <endpoint-ip>` (общим
   счётом до ~30 с).
4. Перезапустить демон, `bottle status` — бутылок нет (демон перезапустился
   с чистой картой), host-клиент остался работать.

**Ожидаемый результат.** Named pipe демона умирает вместе с процессом;
служба закрывает сессию и снимает её маршруты — строки `/32` исчезают из
`Get-NetRoute` **не дольше чем за 10 с** (обычно сразу: по одному
`Remove-NetRoute` на маршрут). В `routes.jsonl` появляются записи
`"op":"del"` с номером умершей сессии. Клиент вендора продолжает
работать (управления им нет — спека §7.2), но его endpoint больше не
запинован.

**Где смотреть при провале.** `routes.jsonl` — дошла ли запись `del`;
служба жива: `sc.exe query BottleForAppsRouteHelper`; остатки маршрутов
уберёт сверка при следующем рестарте службы (пункт 4) — но сам факт
«пережили смерть демона» = провал пункта.

## 4. kill -9 службы → перезапуск → сверка убирает сирот

**Шаги.**
1. Host-бутылка поднята; маршруты endpoint'а видны в `Get-NetRoute`.
2. `taskkill /f /im bottle-svc.exe` — служба убита вместе с pipe.
3. Убедиться: маршруты endpoint'а ОСТАЛИСЬ в ОС (убирать некому — это
   сироты), а в `%PROGRAMDATA%\BottleForApps\routes.jsonl` они всё ещё
   числятся в live-set.
4. `sc.exe start BottleForAppsRouteHelper` (или перезагрузка — служба с
   автозапуском).
5. `Get-NetRoute | findstr <endpoint-ip>`; хвост `routes.jsonl`.

**Ожидаемый результат.** При старте служба сворачивает журнал с ОС:
маршруты-сироты (в ОС есть, живых сессий нет) удаляются через
`Remove-NetRoute`, в `routes.jsonl` пишутся `del`; `Get-NetRoute` чист.
Если host-бутылка была активна — её pin-маршруты тоже сняты сверкой
(для новой службы та сессия мертва): relays продолжали работать (привязаны
к адаптеру), а при необходимости маршрут восстанавливается
`bottle stop corp-vpn` → `bottle start corp-vpn`.

**Где смотреть при провале.** `sc.exe query BottleForAppsRouteHelper`
(запустилась ли служба); хвост `routes.jsonl` (записи сверки); состояние
демона в его консоли — ошибки обращения к службе до её рестарта
нормальны (клиент службы пересоздаётся при обрывах).

## 5. `wsl --shutdown` → env-бутылки прошли Degraded и поднялись сами

**Шаги.**
1. Подняты обе бутылки: env + host.
2. `wsl --shutdown`, подождать ~10 с.
3. `bottle status` — сразу после выключения и затем каждые 15–20 с
   в течение ~3 мин.
4. По завершении проверить работоспособность env-бутылки (SOCKS5-curl /
   RDP-порт) и host-бутылки.

**Ожидаемый результат.** Env-бутылка в течение health-периода (10 с)
переводится в `Degraded (агент аплаенса не отвечает…)`; демон с бэкоффом
5/15/60 с поднимает аплаенс и пере-поднимает бутылки — обычно в течение
**до ~2 минут** состояние возвращается в `up`, SOCKS5/пробросы снова
отвечают (динамические порты закрепляются заново — сверьте номера с
`bottle status`). Host-бутылка: если её VPN-интерфейс жив (клиент на
хосте, WSL его не касался) — остаётся `up` и не трогается вовсе; если
интерфейс умер — бутылка переводится в `stopped` (снимаются её маршруты и
релеи).

**Где смотреть при провале.** Журнал демона: «агент аплаенса не
отвечает…», «восстановление env-бутылок»; `bottle status` (маркеры
`Degraded`/`stopped`); `wsl -l -v` — дистрибутив `bottleforapps`
существует; после восстановления — `wsl -d bottleforapps -- ip netns list`.

## 6. Двойной start / стоп-шторм параллельными CLI

**Шаги.**
1. Открыть 3 окна PowerShell.
2. Окна 1 и 2 одновременно: `bottle start office-a` (двойной старт).
3. Не дожидаясь — окно 3: `bottle status` и `bottle list` (несколько раз,
   пока старт идёт).
4. Затем окна 1 и 2 одновременно: `bottle stop office-a` (двойной стоп).
5. `netstat -ano | findstr <порт>`; `bottle status`.

**Ожидаемый результат.** `status`/`list` отвечают сразу, не дожидаясь
чужого `start` (CLI обрабатываются параллельно). Второй `start`
поднятой бутылки — предупреждение, состояние не меняется; повторный
`stop` остановленной — аналогично. Итог консистентен: в `netstat` один
слушатель на порт (без дублей), `bottle status` показывает одно
состояние на бутылку, осиротевших портов нет. Известная оговорка: если
аплаенс «завис» (агент жив, но не отвечает), `start` может ждать до
~60 с (таймауты RPC демона) и завершится явной ошибкой — это ожидаемое
поведение, не шторм-дефект.

**Где смотреть при провале.** Журнал демона (последовательность
Up/Down, предупреждения дубликатов); `netstat -ano | findstr <порт>`
(два слушателя = дефект); повторить пункт после `wsl --shutdown` +
успешного восстановления (пункт 5), чтобы исключить зависший агент.

## 7. Kill switch вендора (честное ограничение)

**Шаги.**
1. В настройках фирменного клиента найти опцию вида «блокировать трафик
   без VPN» / «Block connections» / «Secure DNS» (AnyConnect:
   «Block unauthorized connections»; FortiClient: kill switch). Если
   опции нет — пункт отмечается как неприменимый.
2. Включить опцию, затем `bottle start office-a` (env-бутылка поверх
   чужого VPN). Наблюдать поведение.
3. Отключить опцию, повторить старт env-бутылки.

**Ожидаемый результат.** С включённым kill switch вендора второй VPN
может не подняться или его трафик блокируется фильтром вендора — это
ограничение фирменного клиента на стороне Windows, а не дефект
BottleForApps (фильтр стоит ниже/выше наших туннелей и решает сам).
BottleForApps при этом не молчит и не врёт: env-бутылка честно уходит в
`failed (туннель не поднялся: handshake timeout)` — с понятной причиной.
Обход: отключить опцию в клиенте (тогда всё работает — вернуться к
пункту 1).

**Где смотреть при провале.** Журнал/статус фирменного клиента (что он
написал про заблокированные подключения); `bottle show office-a`
(причина); журнал демона — резолв endpoint'а и handshake. «Провалом»
пункта считается не сам заблокированный VPN, а неинформативное
поведение бутылки (молчаливый `up` без трафика, зависший `start`).

## 8. Сон/резюме ноутбука → health-цикл восстановил env

**Шаги.**
1. Поднять env-бутылку (+ host по желанию).
2. Усыпить машину (закрыть крышку / Пуск → Спящий режим) на ≥1 минуту.
3. Разбудить; `bottle status` каждые 15–20 с в течение ~3 мин.
4. Проверить SOCKS5/RDP env-бутылки после восстановления.

**Ожидаемый результат.** Как в пункте 5: после пробуждения WSL-аплаенс
мёртв/дезориентирован — бутылки проходят `Degraded`, затем health-цикл
(те же 10 с + бэкофф) сам возвращает их в `up`, обычно до ~2 минут;
ручных команд не требуется. Host-бутылка с живым интерфейсом переживает
сон без изменений состояния.

**Где смотреть при провале.** Журнал демона (метки Degraded/восстановления
с таймингами); `bottle status`; если восстановление не наступило —
`wsl -l -v` (дистрибутив на месте?) и повторный прогон пункта 5 (там же
детали).

## Итог

Этап M2 считается принятым, когда все восемь пунктов отмечены `[x]` (либо
`[n/a]` для неприменимого kill switch) на одной машине одним прогоном, и
при этом пункт 1 выполнялся с реальным фирменным клиентом и реальным
конфиг-VPN. Найденные при приёмке дефекты фиксируются в задачах до
закрытия M2; замечания по UX/DX переносятся в M3 (`doctor`, файловые
журналы, установщик).
