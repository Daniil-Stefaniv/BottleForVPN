# Чеклист ручной приёмки M1

Дата: 2026-09-30 · Этап: M1 (вертикальный срез env-бутылки, спека §14)

Чеклист закрывает критерий готовности M1: *«Две env-бутылки с разными
WG-конфигами одновременно; каждая выходит через свой туннель; endpoint'ы —
через физику (проверено трассировкой); RDP работает»*. Проводится вручную
на машине с Windows 10/11 и WSL2 (режим сети NAT — по умолчанию).

Подготовка (общая для всех пунктов):

- собраны `bottled.exe` и `bottle.exe` (`cargo build --release -p daemon -p cli`);
- собран rootfs-апплайенс (`bash appliance/build-rootfs.sh`, нужен docker)
  — `artifacts/bottleforapps-rootfs.tar.gz`;
- демон запущен: `bottled --data-dir <DataDir> --rootfs <rootfs.tar.gz>`
  (каталог данных лучше держать отдельным, чтобы приёмку можно было
  повторить с чистого состояния);
- для пунктов 2–3 нужны **два реальных WireGuard-конфига** с разными
  внешними IP (например, два разных VPN-провайдера/сервера);
- профиль каждой бутылки — файл `<DataDir>\bottles\<id>.toml` + копия
  конфига `<id>.conf` рядом (формат — спека §5.1), например:

  ```toml
  id = "office-a"
  name = "Офис А"
  kind = "env"

  [vpn]
  protocol = "wireguard"
  config = "office-a.conf"

  [expose]
  socks5 = 0
  forwards = [{ listen = 0, target = "10.20.30.15:3389" }]
  ```

  (`socks5 = 0` и `listen = 0` — автоподбор порта; фактический порт виден
  в `bottle status`).

Обозначение результата: каждый пункт помечается `[ ]` при провале либо
`[x]` при успехе; при провале заполняется «Что смотрели».

---

## 1. Две бутылки с разными WG-конфигами одновременно

**Шаги.**
1. Создать профили `office-a` и `office-b` с разными WG-конфигами
   (разные приватные ключи и endpoint'ы).
2. `bottle start office-a`, дождаться успеха.
3. `bottle start office-b`, дождаться успеха.
4. `bottle status`.

**Ожидаемый результат.** Обе бутылки в `status` в состоянии `up`, у каждой
своя строка `socks5 127.0.0.1:<порт>` с разными портами; ошибки «порт
занят» отсутствуют (порты автоподобраны из 49152–65535).

**Где смотреть при провале.** `bottle show <id>` (причина в `failed
(...)`); журналы демона — вывод `bottled` в консоли (каталог
`<DataDir>\logs` заполняется на M2); состояние VM: `wsl -d bottleforapps
-- ip netns list` — должны быть `bottle-office-a` и `bottle-office-b`, и
`wsl -d bottleforapps -- ss -ltn` — мосты агента на портах из status.

## 2. Каждая SOCKS5 выходит через свой туннель

**Шаги.**
1. Из `bottle status` выписать порты SOCKS5 обеих бутылок (далее `PA`,
   `PB`).
2. `curl --socks5 127.0.0.1:<PA> https://api.ipify.org`
3. `curl --socks5 127.0.0.1:<PB> https://api.ipify.org`

**Ожидаемый результат.** Команды возвращают два **разных** внешних IP —
по одному на туннель; оба отличаются от внешнего IP машины без бутылок
(проверить: `curl https://api.ipify.org` напрямую).

**Где смотреть при провале.** Если оба запроса дают одинаковый IP —
конфиги ведут на один сервер (проверить `Endpoint` в `<id>.conf`); если
curl не подключается к SOCKS5 — `bottle status` (бутылки `up`?), порт из
строки `socks5`; handshake туннеля: `wsl -d bottleforapps -- ip netns
exec bottle-office-a wg show` (последний handshake, счётчики трафика).

## 3. Endpoint'ы идут через физику, а не через соседний туннель

**Шаги.**
1. Поднять обе бутылки (пункт 1).
2. На WG-сервере бутылки A посмотреть, с какого адреса приходят
   пакеты клиента: `wg show` (поле `endpoint` пира), либо
   `tcpdump -ni any udp port <порт сервера A>`.
3. Повторить для сервера B.

**Ожидаемый результат.** На каждом WG-сервере виден **публичный IP
физической сети хоста** (тот же, что показывает `curl https://api.ipify.org`
напрямую), а не внутренний адрес другого туннеля (10.99.x.x / адрес из
AllowedIPs соседа). Пакеты уходят через default namespace VM → eth0 →
NAT WSL → физический адаптер.

**Где смотреть при провале.** Внутри VM: `wsl -d bottleforapps -- ip
netns exec bottle-office-a ip route` — маршрут до endpoint'а `/32` должен
идти через шлюз veth (10.77.<idx>.1), а не через `wg`-интерфейс;
`wsl -d bottleforapps -- iptables -t nat -S | grep MASQUERADE` — правило
для подсети 10.77.0.0/16 на eth0.

## 4. RDP через TCP-проброс

**Шаги.**
1. В профиле бутылки задать проброс до рабочего стола:
   `forwards = [{ listen = 0, target = "<RDP-хост>:3389" }]` (хост —
   адрес, доступный из-за VPN).
2. `bottle start <id>`, из `bottle status` выписать порт строки
   `rdp <target> → 127.0.0.1:<порт>`.
3. Подключиться: `mstsc /v:127.0.0.1:<порт>`.

**Ожидаемый результат.** mstsc показывает экран удалённого рабочего
стола; сессия стабильна (проброс — «глухая» пересылка байтов, RDP-шрифты
и ввод работают).

**Где смотреть при провале.** Проверить достижимость цели изнутри
туннеля: `wsl -d bottleforapps -- ip netns exec bottle-<id> nc -vz -w 3
<RDP-хост> 3389` (или `wget`); порт в status (автоподбор мог смениться
после рестарта); слушатели на хосте: `netstat -ano | findstr <порт>` —
процесс bottled.

## 5. `bottle stop` убирает namespace без остатков

**Шаги.**
1. `bottle stop office-a` (при поднятой второй бутылке — `office-b`
   остаётся поднята).
2. `wsl -d bottleforapps -- ip netns list`.

**Ожидаемый результат.** `ip netns list` пуст (нет `bottle-*`), либо —
если вторая бутылка ещё поднята — остаётся только её namespace; повторный
`bottle status` не показывает остановленную бутылку; её порт SOCKS5 на
127.0.0.1 закрыт (`netstat -ano | findstr <порт>` пуст).

**Где смотреть при провале.** Остаточный namespace: `wsl -d
bottleforapps -- ip netns list`; veth-пары в default ns: `wsl -d
bottleforapps -- ip link | findstr /R "p[0-9] b[0-9]"`; ответ агента в
выводе демона (`bottled` в консоли) — отказ `Down` виден в журнале.

## 6. Перезапуск WSL восстанавливается вручную

**Шаги.**
1. С поднятой бутылкой выполнить `wsl --shutdown`, подождать ~10 с.
2. `bottle status`.

**Ожидаемый результат.** Бутылка не числится `up` (после перезапуска VM
агент при первом обращении стартует заново и сносит `bottle-*`
namespace'ы; авто-восстановление — только в M2). Ручное восстановление:
`bottle start <id>` снова приводит к `up` (демон переимпортирует/будит
аплаенс и поднимает бутылку с нуля).

**Где смотреть при провале.** `wsl -l -v` — дистрибутив `bottleforapps`
существует; после `bottle start` — вывод демона: ошибки соединения с
агентом (токен `<DataDir>\appliance-token` на месте?), handshake
туннеля; `wsl -d bottleforapps -- ip netns list`.

## Итог

Этап M1 считается принятым, когда все шесть пунктов отмечены `[x]` на
одной машине одним прогоном. Найденные при приёмке дефекты фиксируются
в задачах до закрытия M1; замечания по UX/DX можно переносить в M2/M3
(host-бутылки, `doctor`, `logs export`).
