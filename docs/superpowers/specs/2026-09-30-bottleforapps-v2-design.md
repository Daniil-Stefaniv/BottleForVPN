# BottleForApps v2 — спецификация дизайна

Дата: 2026-09-30
Статус: согласованный дизайн (одобрены все секции), ожидает ревью спеки
Автор решения: Daniil (в соавторстве с ZCode, скилл brainstorming)

## 1. Контекст и проблема

BottleForApps v1 (тег `v1-mvp`) — C#/.NET-приложение, позволяющее одновременно держать
несколько связок VPN + RDP: точечные маршруты `/32`/`/128` к публичным endpoint VPN через
физический шлюз + локальный TCP-релей, привязанный к VPN-интерфейсу.

Решено переписать проект с нуля. Все четыре мотивации переписывания (по выбору владельца):

1. **Код и архитектура** — проект нарос без плана (MVP + большая пачка неподтверждённых
   изменений); сложно понимать, доверять и дорабатывать.
2. **Надёжность поведения** — гонки, поведение при сбоях, остаточные маршруты и краевые
   случаи не продуманы и не протестированы.
3. **Схема изоляции** — маршруты + релей = уловка в общей таблице маршрутов ОС; VPN-клиенты
   «видят» друг друга, kill switch и борьба за DNS/default route не решаются в принципе.
4. **Стек** — выбранное сочетание (C#/.NET + Photino + web-панель) не устраивает.

Идея продукта неизменна: **несколько разных VPN-приложений с совершенно разными настройками
работают одновременно, не зная друг о друге, и уходят в интернет через изначальную
(физическую) сеть компьютера.**

## 2. Цели и не-цели

### Цели первой версии (v2.0)

- Конфиг-VPN (WireGuard, OpenVPN) — одновременная работа любого количества туннелей с
  **конструктивной** изоляцией: собственный сетевой namespace на бутылку (своя таблица
  маршрутов, свой DNS, свой default route), исходящий трафик — через NAT физического
  адаптера хоста.
- Фирменные GUI-VPN-клиенты (AnyConnect, FortiClient и т.п.) — работа на хосте через
  точечные маршруты endpoint'ов (схема v1, переписанная как минимальный надёжный движок).
- Каждая бутылка предоставляет наружу на `127.0.0.1`: SOCKS5-прокси и TCP-пробросы
  (для RDP: `mstsc` подключается на `127.0.0.1:<порт>`).
- Windows 10/11, включая Home (изоляция — через WSL2, без Hyper-V-требований и без
  драйверов ядра: туннели поднимаются в Linux userspace через `/dev/net/tun`).
- Распространяемый продукт: MSI-установщик, portable-вариант, диагностика (`doctor`),
  журнал логов с экспортом, документация.
- Стек: Rust (ядро, CLI, служба, агент); GUI — позже отдельным этапом (Tauri).

### Не-цели первой версии (осознанные границы)

- macOS — не в v2.0 (порт апплайнса на Virtualization.framework — этап M4; архитектурных
  препятствий нет: ядро кроссплатформенное по построению).
- Прозрачный перехват трафика произвольных приложений без настройки прокси — нет.
- Автоотключение фирменных VPN-клиентов после остановки бутылки — нет (нет универсального
  API; документированное ограничение, как в v1).
- UDP-релей для RDP — нет (mstsc использует TCP; как в v1).
- GUI, автообновление самого приложения, телеметрия — нет.
- UAC-fallback для host-бутылок без службы — нет: без `bottle-svc` host-бутылки отключены
  с понятным объяснением (меньше веток поведения, чем в v1).

## 3. Рассмотренные подходы и выбор

| Подход | Суть | Вердикт |
|---|---|---|
| **1. WSL2-апплайенс + гибрид** | конфиг-VPN в network namespace внутри WSL2-дистрибуции; GUI-клиенты на хосте с точечными маршрутами | **Выбран.** Изоляция по построению, без драйверов, работает на Home, шов для будущей VM-изоляции |
| 2. Полная виртуализация | каждой бутылке по VM (Hyper-V/Windows Sandbox), включая GUI-клиентов | Отклонён для v2.0: Pro-only, гигабайты RAM на бутылку, лицензии Windows-VM, объём ×2. Оставлен как будущий уровень изоляции `vm` без переделки модели |
| 3. Без VM (v1-схема на Rust) | все VPN на хосте через WinTun-адаптеры и маршруты | Отклонён: не решает главное требование («не знают друг о друге»), возвращает подпись драйверов и конфликты с антивирусами |

Ключевой факт, определивший выбор: пер-процессные сетевые стеки (network namespaces) —
механизм Linux; на Windows их даёт только VM. WSL2 — самая лёгкая VM, доступная на Home.

## 4. Компоненты и процессы

Три процесса с непересекающимися зонами ответственности:

```
Windows (хост)                                Апплайенс (WSL2 — Linux VM)
┌─────────────────────────────────┐           ┌──────────────────────────────────┐
│ bottled.exe — демон в сессии    │  RPC(TCP, │ bottle-agent (root)              │
│   пользователя, БЕЗ прав админа │  токен)   │   ├ netns office-a: WG  + relay  │
│   • профили, жизненный цикл     │──────────▶│   ├ netns office-b: OVPN+ relay  │
│   • слушатели 127.0.0.1:SOCKS5/ │   данные  │   └ default ns: eth0             │
│     TCP-пробросы                │◀──────────│      (NAT → физика хоста)        │
├─────────────────────────────────┤           └──────────────────────────────────┘
│ bottle-svc.exe — сервис SYSTEM: │           Апплайенс stateless: все настройки
│   ТОЛЬКО add/del host-маршрутов │           живут на Windows, в VM передаются
│   (named pipe, валидация+журнал)│           на время сессии бутылки
├─────────────────────────────────┤
│ bottle.exe — тонкий CLI-клиент  │
│   → общается с bottled          │
└─────────────────────────────────┘
```

### 4.1. `bottled.exe` — демон (владелец всего)

- Работает в сессии пользователя, прав администратора не требует. Single-instance
  (именованный mutex). Автозапуск — опция установщика.
- Владеет: хранилищем профилей, стейт-машиной всех бутылок, слушателями `127.0.0.1`
  (SOCKS5 + TCP-пробросы для env-бутылок; relay для host-бутылок — внутри демона),
  соединением с апплайенсом, запуском фирменных клиентов, перепроверкой DNS endpoint'ов,
  диагностическими журналами.
- Является единственным клиентом `bottle-svc` и `bottle-agent`.
- В отличие от v1 (бутылка = окно терминала): один демон = все бутылки = единый статус,
  единая диагностика, естественная точка для будущего GUI.

### 4.2. `bottle-svc.exe` — привилегированный минимум (служба Windows, SYSTEM)

- Единственная обязанность: операции над host-маршрутами `add`/`del`/`cleanup`.
  Никакого запуска процессов, никакого произвольного ввода.
- Транспорт: именованный канал `\\.\pipe\bottleforapps-routes`, ACL: SYSTEM и
  администраторы — полный доступ, интерактивные пользователи — чтение/запись.
- Валидация на входе: только `/32` (IPv4) и `/128` (IPv6) host-маршруты; адреса
  endpoint — публичные (loopback, link-local, multicast отвергаются); шлюз — текущий
  шлюз указанного физического интерфейса.
- Журнал добавленных маршрутов (JSONL) + сверка при старте службы (см. §9).
- Устанавливается MSI-инсталлятором один раз (единый UAC-запрос при установке).

### 4.3. `bottle-agent` — исполнитель внутри апплайнса (Linux, root)

- Стартует автоматически через `boot.command` в `/etc/wsl.conf` дистрибуции
  `bottleforapps`.
- Управляет namespace'ами: `bottle-<id>` на каждую env-бутылку — создание veth-пары,
  `resolv.conf` namespace'а, запуск туннеля и relay, разбор.
- Контрольный канал: TCP на IP виртуальной машины WSL (доступен только хосту через
  vswitch, не из LAN), аутентификация токеном (генерируется при импорте дистрибуции,
  хранится в хранилище профилей с ACL пользователя и внутри VM с правами 0600 root).
  Протокол: versioned length-prefixed JSON; whitelist операций: `up`, `down`, `status`,
  `shutdown`.
- Stateless: конфиги туннелей передаются демоном на время сессии и живут только в
  tmpfs (`/run/bottles/<id>/`); после `down` или перезапуска VM ничего не остаётся.

### 4.4. `bottle.exe` — CLI

Тонкий клиент демона через именованный канал `\\.\pipe\bottled` (ACL — текущий
пользователь). Пользовательские строки — на русском (как в v1), идентификаторы кода —
английские.

Команды: `create`, `list`, `show`, `start`, `stop`, `status`, `doctor`, `logs export`,
`routes cleanup`, `upgrade`. GUI (Tauri) на этапе M4 использует тот же RPC, что и CLI.

## 5. Модель данных

### 5.1. Профиль бутылки — TOML, `%LOCALAPPDATA%\BottleForApps\bottles\<id>.toml`

```toml
id = "office-a"                  # [a-z0-9-], имя файла = id
name = "Офис А"                  # человекочитаемое
kind = "env"                     # "env" | "host"

# ---- kind = "env" ----
[vpn]
protocol = "wireguard"           # "wireguard" | "openvpn"
config = "wg-office-a.conf"      # копия файла в хранилище; содержит секреты

# ---- kind = "host" ----
# [vpn]
# client  = "C:\\Program Files\\Vendor\\vpn.exe"
# args    = "connect office"     # опционально
# endpoints = ["vpn.example.com"]  # повторяемый; DNS перепроверяется
# interface = "Vendor Adapter"     # опционально; иначе автоопределение

[expose]                          # одинаково для обоих kind
socks5 = 0                        # порт на 127.0.0.1; 0 = автоподбор
forwards = [{ listen = 0, target = "10.20.30.15:3389" }]  # listen 0 = автоподбор
dns = "10.20.30.1"                # опционально; DNS внутри namespace (env)
                                  # или документируется как неиспользуемый (host)
launch = "mstsc"                  # опционально: команда, запускаемая после "up"
```

- Каталог хранилища — ACL только на текущего пользователя (там секреты).
- Автоподбор портов: из диапазона 49152–65535, порт закрепляется на сессию и виден в
  `status`; явный занятый порт — ошибка с указанием, кем занят.

### 5.2. Состояния бутылки (стейт-машина демона)

`stopped → starting → up → stopping → stopped`; побочные состояния: `degraded`
(туннель жив, часть функций недоступна — напр. DNS), `failed` (не поднялась; причина в
статусе и журнале). Переходы идемпотентны: повторный `start` на `up` — no-op с предупреждением,
повторный `stop` — no-op.

## 6. Сетевой тракт апплайнса

Путь данных env-бутылки (пример RDP):

```
mstsc → 127.0.0.1:5501 (bottled)
      → TCP → VM_IP:5501 (мост агента в default ns)
      → veth → relay внутри netns office-a
      → wg0 (туннель в netns): plaintext идёт по default route namespace в туннель
      → зашифрованный внешний пакет к endpoint VPN → маршрут до endpoint через veth
      → default ns → eth0 VM
      → WSL NAT → физический адаптер хоста → интернет → endpoint VPN → офис → RDP
```

- Namespace `bottle-<id>`: собственная таблица маршрутов (default route только через
  туннель после handshake — весь трафик namespace идёт в VPN), собственный
  `/etc/netns/bottle-<id>/resolv.conf` (из `expose.dns`).
- veth-пара: `b<id>` внутри namespace ↔ `p<id>` в default ns; relay слушает на стороне
  namespace, мост агента в default ns пересылает соединения с `VM_IP:<порт>` внутрь.
- Туннели — userspace: `wireguard-go` и `openvpn` через `/dev/net/tun`; модулей ядра и
  внешних драйверов нет ни в VM, ни на Windows.
- Демон подключается к `VM_IP` напрямую (IP узнаётся у агента/через `wsl.exe hostname -I`);
  на автоматику localhost-forwarding WSL **не полагаемся** (исторически ненадёжна).
- Требование к режиму сети WSL — NAT (по умолчанию). `doctor` детектирует
  `networkingMode=mirrored` и требует переключить на NAT.

## 7. Жизненные циклы

### 7.1. Env-бутылка: `start`

1. Демон валидирует профиль, резервирует порты на `127.0.0.1`.
2. Демон гарантирует апплайенс: WSL дистрибуция импортирована, VM запущена, агент
   отвечает, версии протокола совместимы; иначе — импорт (`wsl --import`) / запуск /
   понятная ошибка.
3. Демон → агент `up(id, protocol, config, dns, forwards)`: конфиг передаётся по
   аутентифицированному каналу и пишется в tmpfs.
4. Агент: создаёт namespace+veth+resolv.conf, запускает туннель, ждёт handshake
   (≤30 с WireGuard, ≤60 с OpenVPN; иначе `failed` с журналом).
5. Агент: запускает relay внутри namespace, поднимает мост в default ns, отвечает `ready`.
6. Демон: открывает слушатели `127.0.0.1`, пробрасывает данные в VM. Состояние `up`;
   `status` показывает проверенный путь (как карточка v1).

`stop` — в обратном порядке, идемпотентно; тайна-конфиг исчезает вместе с tmpfs.
`launch` (если задан) выполняется после перехода в `up` (например, `mstsc` на проброс).

### 7.2. Host-бутылка: `start`

1. Демон собирает endpoint'ы всех активных бутылок, резолвит DNS.
2. Демон → `bottle-svc`: точечные маршруты `/32`/`/128` endpoint'ов **чужих** VPN через
   физический шлюз (каждый маршрут валидируется и журналируется сервисом).
3. Демон запускает фирменный клиент (в сессии пользователя, окружение наследуется).
   Ожидание VPN-интерфейса ≤120 с: по `expose.interface`, иначе автоопределение —
   диф-снимок интерфейсов до/после; появился ровно один новый `Up` — берём его,
   несколько — ошибка с просьбой указать `interface`.
4. Relay стартуют в демоне, сокеты привязаны к VPN-адаптеру (`IP_UNICAST_IF` /
   `IPV6_UNICAST_IF`) — детерминированный выход вопреки борьбе за маршруты.
5. Фоновая перепроверка DNS endpoint'ов каждые 30 с: новые адреса получают маршруты,
   старые живут до конца сессии (не рвать установленное соединение; поведение v1).
6. `stop`: relay вниз, маршруты сняты через `bottle-svc`. Клиент-вендор остаётся
   работать (документированное ограничение).

Особые случаи: тот же вендор-клиент уже запущен — предупреждение, повторное
использование существующего интерфейса, если он совпал; две host-бутылки одного вендора
не поддерживаются (doctor предупреждает).

## 8. RPC-протоколы (кратко)

| Канал | Транспорт | Аутентификация | Операции |
|---|---|---|---|
| CLI → демон | named pipe `\\.\pipe\bottled` | ACL канала (текущий пользователь) | create/list/show/start/stop/status/doctor/logs/cleanup/upgrade |
| Демон → `bottle-svc` | named pipe `\\.\pipe\bottleforapps-routes` | ACL канала | route.add, route.del, routes.cleanup, routes.journal |
| Демон → агент | TCP `VM_IP:7777` | токен (при импорте), versioned handshake | up, down, status, shutdown |

Формат сообщений везде: length-prefixed JSON с полем версии протокола. Несовпадение
версий агента и демона — блокирующая ошибка с подсказкой `bottle upgrade`.

## 9. Надёжность

Принцип: **у каждого эффекта вне процесса есть владелец, журнал и сверка при старте.**
Демон — единственный «мозг»; `bottle-svc` и агент — stateless-исполнители, которые можно
убить и пересоздать.

| Сбой | Поведение |
|---|---|
| Агент упал / VM перезапущена | Агент стартует из `boot.command`, при старте сносит все `bottle-*` namespace'ы, сообщает демону. Демон по политике (по умолчанию) автоматически поднимает env-бутылки; host-бутылки → `stopped` (нужен человек для клиента) |
| WSL гасит VM при простое | Пока жива хоть одна бутылка, процессы в VM держат её активной; обрыв control-соединения демоном детектится по таймауту и обрабатывается как перезапуск VM |
| `bottle-svc` упал посреди операции | Журнал маршрутов в JSONL; при старте служба сверяет журнал с живыми сессиями демона и убирает лишнее |
| Остаточные маршруты после краха демона | Та же сверка; ручной вариант — `bottle routes cleanup`. Перезагрузка Windows стирает ActiveStore-маршруты сами (как в v1) |
| Порт `127.0.0.1` занят | Автоподбор (если `0`) или понятная ошибка с владельцем порта |
| Таймаут handshake туннеля | Бутылка → `failed`, namespace разобран, причина в `status` и журнале |
| IPv6-endpoint без IPv6-шлюза у физики | Блокируем запуск с объяснением (поведение v1) |
| Kill switch вендора | Документированное ограничение host-бутылок; `doctor` объясняет, как выявить |
| Сон/резюме хоста | Демон детектит (события питания), пересверяет состояние всех бутылок и восстанавливает по политике |
| Второй экземпляр демона | Single-instance mutex; второй CLI-запрос подключается к живому демону |

## 10. Безопасность

- Привилегированные поверхности минимальны: служба — только host-маршруты с жёсткой
  валидацией (никакого exec); агент — только lifecycle namespace'ов за токеном.
- Токен агента и конфиги VPN — секреты: ACL на хранилище (только пользователь), tmpfs в
  VM, маскирование в журналах (маскируются аргументы запуска клиентов и содержимое
  конфигов; пароли не пишутся никогда).
- Модель угроз для обоих каналов — другие локальные пользователи машины: named pipe ACL
  + токен + недоступность control-порта агента из LAN (vswitch WSL — только хост).
- Телеметрии нет; данные никуда не отправляются; `logs export` формирует ZIP локально с
  предупреждением о содержимом (IP, имена интерфейсов, endpoint — как в v1).

## 11. Установка и распространение

Два уровня установки:

1. **Полная — MSI (WiX), один UAC-запрос:**
   - ставит службу `bottle-svc`, `bottled.exe`/`bottle.exe` в PATH, опция автозапуска демона;
   - включает компоненты WSL (`wsl --install --no-distribution`; возможная перезагрузка
     обрабатывается явно: установщик завершает установку после перезагрузки);
   - импорт апплайнса — при первом запуске демона (per-user `wsl --import`, без админа).
2. **Portable — zip без прав администратора:** только env-бутылки; host-бутылки отключены
   с объяснением в `doctor` (WSL должен быть включён в системе заранее).

Апплайенс: rootfs-tarball (основа Alpine; пакеты `openvpn`, `wireguard-go`, iptables)
собирается в `appliance/` и входит в оба пакета; `bottle upgrade` переимпортирует
дистрибуцию (stateless — потерь нет). Подпись кода — обязательна в релизном процессе,
разработку не блокирует.

## 12. Тестирование и CI

- Cargo workspace; CI (GitHub Actions): `cargo fmt --check`, `clippy -D warnings`,
  `cargo test` на каждом PR.
- Юнит-тесты: парсинг TOML-профилей, валидация IP/портов/endpoint'ов, стейт-машина,
  маскирование логов.
- Агент — интеграционные тесты на Linux-раннере: реальные netns/veth, handshake
  `wireguard-go` с тестовым WG-сервером (контейнер в CI), разбор после `kill -9`.
- Windows-раннер с WSL2: полный путь env-бутылки (импорт дистрибуции → up → SOCKS5/RDP
  forward → down); тесты `bottle-svc` (раннер под админом: добавление/снятие/сверка
  маршрутов через `Get-NetRoute`).
- Destructive-набор (по роли тестировщика-разрушителя): двойной `start`, `kill -9`
  каждого из трёх процессов посреди операций, занятые порты, отсутствие/отключённый
  WSL, mirrored-режим сети WSL, v6-endpoint без v6-шлюза, 100 одновременных соединений
  через relay, сон/резюме.
- Ручной релизный чеклист: два реальных VPN (WG + OpenVPN) + один фирменный клиент
  одновременно, RDP через каждую бутылку.

## 14. Дорожная карта

| Этап | Содержание | Критерий готовности |
|---|---|---|
| M0 | Скелет workspace, CI, типы RPC, ручная сборка апплайнса | CI зелёный, протоколы согласованы |
| M1 | Вертикальный срез env-бутылки: WG + SOCKS5 + RDP-проброс на одной машине | Две env-бутылки с разными WG-конфигами одновременно; каждая выходит через свой туннель; endpoint'ы — через физику (проверено трассировкой); RDP работает |
| M2 | Надёжность (сверки, журналы, cleanup) + `bottle-svc` + host-бутылки | Destructive-набор проходит; host-бутылка с реальным клиентом работает параллельно с env |
| M3 | Установщики (MSI + portable), `doctor`, `logs export`, документация | Чистая машина: установка → первая бутылка без ручных шаманств |
| M4 (позже) | Tauri GUI, macOS-порт апплайнса (Virtualization.framework) | Отдельная спека |

## 15. Риски и меры

| Риск | Мера |
|---|---|
| WSL2 отключён корпоративной политикой | `doctor` диагностирует; env-бутылки недоступны, host-бутылки работают; portable-тир без WSL-требований к установке |
| Режимы сети WSL меняются между сборками Windows | Требуем NAT-режим, детектируем mirrored; прямое подключение к `VM_IP`, без localhost-forwarding |
| `wireguard-go`/пакеты Alpine недоступны/несовместимы | Версии закреплены в сборке апплайнса; при необходимости — сборка из исходников в `appliance/` |
| WSL2 на CI-раннерах ограничен | Фолбэк: полные тесты агента на Linux-раннере, Windows-путь — ручной чеклист релиза |
| Дополнительный TCP-скачок внутри VM (мост агента) | Замер в M1; ожидаемо пренебрежимо на фоне шифрования VPN |
